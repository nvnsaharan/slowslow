Core techniques for revision

The patterns behind your resume: idempotency, outbox, locks, caching, retries, DLQ, Kafka, SQS, leases and more, each with how to implement it.

How to use this page

Each topic has: what it is, why it matters, how to implement it, the usual pitfalls (amber) and where you used it (green). Open the ones from your resume first: idempotency, outbox, Kafka, DLQ, caching, zero-downtime deployment.

Correctness under retries
1Idempotency

What: An operation is idempotent if doing it once or many times leaves the system in the same state, and returns the same result. Different from "no duplicates": it is about safe repeats.

Why it matters: Networks, queues and clients retry. SQS and Kafka are at-least-once. Without idempotency a retry charges twice, sends two emails, or cancels two appointments.

How to implement:

  • Pick an idempotency key: client-supplied (Idempotency-Key header), or derived deterministically from the business event (batch_id + msg_id, order_id + action).
  • Store the key with the result in a table with a UNIQUE constraint, in the same transaction as the side effect.
  • On a repeat: key exists and completed, return the stored result. Key exists and in-progress, return 409 or wait. Missing, run it.
  • Prefer natural idempotency first: upserts (INSERT ... ON CONFLICT DO NOTHING), set-to-value instead of increment, status-transition guards (UPDATE ... WHERE status = 'pending').
  • Give keys a TTL longer than the longest retry window.
  • For external side effects (email, payment), pass your key to the provider if it supports one; otherwise record intent in an outbox first.
-- one row per processed key; UNIQUE does the dedupe
CREATE TABLE idempotency (
  key text PRIMARY KEY,
  status text NOT NULL,            -- in_progress | done
  response jsonb,
  created_at timestamptz DEFAULT now()
);

-- Go: claim, do work, record, all in one tx
tx.Exec(`INSERT INTO idempotency(key,status) VALUES($1,'in_progress')
         ON CONFLICT DO NOTHING`, key)
if rowsAffected == 0 { return storedResponse(key) }   // repeat
doWork(tx)
tx.Exec(`UPDATE idempotency SET status='done', response=$2 WHERE key=$1`, key, resp)
tx.Commit()
Say thisMediBuddy: Redis dedupe for wallet recharges and idempotent account deactivation. SnagIt: job_id = blake2b(batch_id||msg_id), seen_messages, status-transition claim at settlement.
Know the catchKey and side effect not in one transaction (crash between them gives a duplicate or a lost action). Key derived from something that changes on retry (timestamp, random id). Hashing the request body but ignoring that two different requests may reuse a key.
2At-least-once, at-most-once, "exactly-once"

What: Delivery guarantees. At-most-once: may lose, never duplicates. At-least-once: never loses, may duplicate. Exactly-once delivery across a network is not achievable; exactly-once effect is at-least-once delivery plus idempotent processing.

Why it matters: This is the sentence interviewers want when you say "exactly-once execution" on a resume.

How to implement:

  • Use at-least-once transport (ack after processing).
  • Make the handler idempotent (topic 1).
  • Kafka offers transactions and idempotent producers for exactly-once within Kafka read-process-write, but side effects outside Kafka still need your own idempotency.
Say thispg-boss "exactly-once execution" at MediBuddy is a job claimed once with idempotent handlers.
Know the catchSaying "exactly-once" without explaining the mechanism. Always say: at-least-once delivery plus idempotency gives exactly-once effect.
3Transactional outbox

What: Write the business change and the "message to send" as rows in the same DB transaction. A separate relay sends outbox rows and marks them sent.

Why it matters: A DB write and a broker publish cannot be atomic. Publishing first loses the DB write on failure; writing first loses the message.

How to implement:

  • Table outbox(id, topic, payload, created_at, sent_at NULL).
  • Relay: SELECT ... WHERE sent_at IS NULL FOR UPDATE SKIP LOCKED LIMIT n, publish, set sent_at, commit.
  • Receivers must dedupe, since the relay can send then crash before marking sent.
  • Alternative: CDC (Debezium) reads the WAL and publishes.
BEGIN;
UPDATE orders SET status='paid' WHERE id=$1;
INSERT INTO outbox(topic,payload) VALUES('order.paid', $2);
COMMIT;
-- relay loop
SELECT id,payload FROM outbox WHERE sent_at IS NULL
ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 100;
Say thisSnagIt orchestrator outbox loop (5 s) sends the compile message after artifactworker writes the row.
Know the catchUnbounded outbox growth (add retention). Ordering across multiple relays. Sending outside the claiming transaction invites duplicates or deadlocks.
4Inbox / deduplication on the consumer

What: Mirror of the outbox: record processed message ids so redelivery does nothing.

Why it matters: Brokers redeliver on timeout or rebalance.

How to implement:

  • Table or Redis key per message id, written in the same transaction as the effect (DB) or with SET key 1 NX EX ttl (Redis).
  • Redis-only dedupe is fast but not atomic with a DB write; accept it only if the effect is itself safe to repeat or can be reconciled.
  • Choose TTL longer than max redelivery delay.
// Redis dedupe (fast path)
ok, _ := rdb.SetNX(ctx, "seen:"+msgID, 1, 24*time.Hour).Result()
if !ok { return nil }          // already handled, ack and skip
if err := handle(msg); err != nil {
    rdb.Del(ctx, "seen:"+msgID) // let a retry through
    return err
}
Say thisMediBuddy Kafka consumer used Redis for idempotent dedupe and failure tracking.
Know the catchMarking seen before success and then crashing (message lost). Marking after success without a lock (two consumers both run it).
Coordination and caching
5Distributed locks, leases and fencing

What: A lock held across processes. A lease is a lock that expires on its own. A fencing token is a monotonically increasing number the protected resource checks to reject a stale holder.

Why it matters: Stops two workers doing the same exclusive work, for example refilling one cache key.

How to implement:

  • Acquire: SET lock:key token NX PX 10000. Token is unique per holder.
  • Release only if you still own it: compare-and-delete in Lua.
  • Renew (heartbeat) while working; cap total hold time.
  • If correctness matters, pass a fencing token to the resource, because a paused process can wake up after its lease expired.
  • Avoid locks when a unique constraint or atomic op can do the job.
-- release.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
Say thisAPMS: lock:<host> with constant value "1" and plain delete is exactly this weakness. SnagIt leases with heartbeat ceiling.
Know the catchPlain DEL in release can delete someone else's lock after yours expired. Clock and GC pauses. Redlock is contested for correctness-critical use.
6Caching patterns and cache stampede

What: Cache-aside (app loads on miss), read-through, write-through, write-behind. Stampede: many requests recompute one expired hot key.

Why it matters: Protects the DB and cuts latency.

How to implement:

  • Cache-aside with TTL; add jitter to TTL so keys do not expire together.
  • Single-flight: one request rebuilds under a lock, others wait or serve stale.
  • Stale-while-revalidate: serve old value while one request refreshes.
  • Negative caching for "not found".
  • Invalidate on write, or accept TTL staleness knowingly.
v, ok := cache.Get(k)
if ok { return v }
if lock.TryAcquire(k, 10*time.Second) {
    defer lock.Release(k)
    if v, ok = cache.Get(k); ok { return v }   // double-check
    v = db.Load(k); cache.Set(k, v, ttl+jitter())
    return v
}
return waitForCache(k, 5*time.Second)
Say thisAPMS: Redis 5 min TTL, SETNX lock, double-checked read, poll for 5 s.
Know the catchCache and DB disagreeing after a failed invalidation. Caching errors. Unbounded keyspace without eviction.
Failure handling and protection
7Retries, exponential backoff and jitter

What: Retry transient failures with growing delays and random spread.

Why it matters: Immediate retries from thousands of clients create retry storms that finish off a struggling service.

How to implement:

  • Retry only idempotent or keyed operations and only transient errors (5xx, timeouts, 429).
  • delay = min(cap, base * 2^attempt) then random between 0 and delay ("full jitter").
  • Set max attempts and an overall deadline.
  • Honour Retry-After.
  • Move to a DLQ after max attempts.
func backoff(attempt int) time.Duration {
    d := time.Duration(math.Min(30, math.Pow(2, float64(attempt)))) * time.Second
    return time.Duration(rand.Int63n(int64(d)))   // full jitter
}
Say thisSnagIt: jittered Retry-After on 404/503, client retries after 3 s and 8 s, throttle retry must outlast DLQ redrive.
Know the catchRetrying non-idempotent calls. Retrying at every layer (multiplies load: 3 x 3 x 3). No deadline.
8Dead-letter queues (DLQ)

What: A side queue for messages that failed too many times.

Why it matters: One poison message must not block the queue forever, and must not vanish.

How to implement:

  • Set maxReceiveCount (SQS redrive policy) or a retry counter header.
  • Alert on DLQ depth and age.
  • Provide a redrive tool and fix the bug before redriving.
  • Keep original payload and error reason.
Say thisResume skill DLQ; SnagIt DLQ redrive window.
Know the catchDLQ without alarms is a silent graveyard. Redriving before the fix recreates the loop.
9Circuit breaker, timeouts, bulkheads

What: Stop calling a failing dependency for a while (open), probe occasionally (half-open), close when healthy. Bulkhead isolates resource pools per dependency.

Why it matters: Fail fast instead of piling up threads and timeouts.

How to implement:

  • Always set timeouts on every network call, shorter than the caller's timeout.
  • Breaker: count failures in a window, open at a threshold, half-open after a cool-down with a few trial calls.
  • Bulkhead: separate connection pools or worker limits per dependency.
  • Fallback: cached or degraded response.
Say thisSnagIt "never 500" 503 policy and four services split by resource profile are bulkheads.
Know the catchNo timeout means the breaker never sees failures. Thresholds too tight cause flapping.
10Rate limiting

What: Cap requests per key per time window. Algorithms: fixed window, sliding window, token bucket, leaky bucket.

Why it matters: Protects dependencies and enforces fairness.

How to implement:

  • Token bucket: tokens refill at rate r, bucket size b, each request takes one.
  • In Redis use a Lua script so read-modify-write is atomic and shared across instances.
  • Return 429 with Retry-After. Key by user, device, IP or API key.
  • Add a global limit for a downstream provider, not just per client.
-- token bucket in Lua (KEYS[1]=bucket, ARGV: rate, burst, now_ms)
local t = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(t[1]) or tonumber(ARGV[2])
local ts = tonumber(t[2]) or tonumber(ARGV[3])
tokens = math.min(ARGV[2], tokens + (ARGV[3]-ts)/1000*ARGV[1])
if tokens < 1 then return 0 end
redis.call("HSET", KEYS[1], "tokens", tokens-1, "ts", ARGV[3])
redis.call("PEXPIRE", KEYS[1], 60000)
return 1
Say thisAdmitted gap in SnagIt: no fleet-wide provider rate limiter; v1 success dropped from 85% to about 41-53% at high rate.
Know the catchPer-instance in-memory limits multiply with replicas. Clock skew across instances.
11Backpressure and load shedding

What: Backpressure slows producers when consumers lag. Load shedding drops or rejects work to keep the system alive.

Why it matters: Without it queues grow until memory or latency explodes.

How to implement:

  • Bound every queue and buffer.
  • Choose a policy when full: block, drop newest, drop oldest, or reject with 429/503.
  • Telemetry should drop; user work should block or reject.
  • Admission control: accept only what you can finish before its deadline.
select {
case ch <- ev:
default:
    droppedEvents.Inc()   // never block the hot path for telemetry
}
Say thisAPMS channel buffer 1000 blocks; SnagIt admission control = drain_rate x deadline.
Know the catchBlocking sends on the request path. Unbounded channels.
Messaging and data stores
12Kafka essentials: partitions, consumer groups, ordering, offsets

What: A topic is split into partitions. Order is guaranteed only within a partition. A consumer group splits partitions among consumers; each partition has one consumer in a group.

Why it matters: Core of your MediBuddy and Zee work.

How to implement:

  • Choose the message key so events that must stay ordered share a partition (e.g. wallet id).
  • Parallelism is capped by partition count.
  • Commit offsets after processing (at-least-once). Auto-commit before processing can lose messages.
  • Handle rebalances: finish or drop in-flight work, avoid long handlers beyond max.poll.interval.
  • Retry topics and a DLQ topic for failures; keep ordering in mind when retrying.
  • Use an idempotent producer (enable.idempotence=true) to avoid producer-side duplicates.
Say thisMediBuddy: 150K+ events/hour with consumer groups and ordering guarantees.
Know the catchHot partitions from a skewed key. Retrying out of order. Slow handlers triggering rebalances.
13SQS: visibility timeout, standard vs FIFO, long polling

What: A received message is hidden for the visibility timeout; if not deleted it reappears.

Why it matters: The mechanism behind retries and leases in many pipelines.

How to implement:

  • Set visibility timeout above the longest handler time, or extend it with heartbeats.
  • Standard: at-least-once, best-effort order, high throughput. FIFO: ordered per group, deduplication id, lower throughput.
  • Long polling (20 s) cuts empty receives.
  • Redrive policy to a DLQ after N receives.
  • Retention caps how long a message can wait; older ones are deleted.
Say thisSnagIt: 5 h retention on blinkit-in versus 14 days assumed; SQS visibility used instead of leader election.
Know the catchHandler slower than visibility timeout causes duplicate processing. Silent loss when retention expires.
14Leases and heartbeats for work distribution

What: Hand out work with an expiring claim; the holder renews it while alive. If it dies the work returns.

Why it matters: Workers die. Without leases work is stuck forever.

How to implement:

  • Lease duration per job type (not one global value).
  • Heartbeat extends the lease up to a ceiling measured from first claim.
  • Reaper requeues expired leases in bounded batches, counts attempts, buries after N.
  • Late result from a former holder: accept if idempotent, but do not tear down the new holder's lease (check holder).
Say thisSnagIt claim.lua, reap.lua, complete.lua.
Know the catchLease shorter than normal work causes duplicate work. Unbounded reaper passes.
15Optimistic vs pessimistic locking, SKIP LOCKED

What: Pessimistic: lock rows before changing (SELECT ... FOR UPDATE). Optimistic: version column, update only if unchanged.

Why it matters: Prevent lost updates.

How to implement:

  • Optimistic: UPDATE t SET ..., v=v+1 WHERE id=$1 AND v=$2; zero rows means retry.
  • Pessimistic for short, high-contention critical sections.
  • FOR UPDATE SKIP LOCKED turns a table into a work queue and lets many workers take different rows.
  • Keep transactions short; set lock_timeout and statement_timeout.
UPDATE jobs SET status='running', worker=$1
WHERE id = (SELECT id FROM jobs WHERE status='ready'
            ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;
Say thispg-boss and the SnagIt outbox both rely on SKIP LOCKED.
Know the catchQueue tables churn dead tuples at high rates (why SnagIt used Redis). Deadlocks from inconsistent lock order.
16Transactions and isolation levels

What: ACID. Isolation levels: read committed (default in Postgres), repeatable read, serializable. Anomalies: dirty read, non-repeatable read, phantom, write skew.

Why it matters: Picking the weakest level that keeps your invariant.

How to implement:

  • Read committed is fine when each statement is self-contained.
  • Use serializable (and retry on 40001) for invariants that span rows.
  • Or enforce the invariant with a constraint, unique index or atomic UPDATE.
  • Batch many small writes into one transaction when atomicity allows (SnagIt settles 500 results per transaction).
Say thisSnagIt statement_timeout 30 s, lock_timeout 10 s on its database.
Know the catchLong transactions block vacuum and hold locks.
17Saga and compensation

What: A long business flow split into local transactions, each with a compensating action if a later step fails.

Why it matters: No distributed transaction across services.

How to implement:

  • Orchestration (a coordinator drives steps) or choreography (services react to events).
  • Each step idempotent and each compensation idempotent.
  • Persist saga state so it survives restarts.
  • Design compensation that is semantically sound (refund, cancel), not literal rollback.
Say thisWorkflow engine for Last Working Day (deactivate account, cancel appointments) is saga-shaped.
Know the catchCompensations that can fail. Visible intermediate states.
18Eventual consistency, CAP and consistency models

What: Under a network partition you choose consistency or availability. Eventual consistency: replicas converge if updates stop.

Why it matters: Vocabulary for design reviews.

How to implement:

  • State where your system sits: Postgres ledger is the strong source of truth; Redis shelf and caches are eventually consistent derived state.
  • Provide a reconcile loop that repairs drift.
  • Read-your-writes only where users need it.
Say thisAPMS learning delay about 6.5 minutes; SnagIt reconcile loop rebuilds the shelf.
Know the catchSaying "CAP says pick two" is shallow. Partitions are not optional; the choice is during a partition.
19Sharding, partitioning and consistent hashing

What: Split data by key across nodes. Consistent hashing minimises key movement when nodes change.

Why it matters: Scale beyond one machine.

How to implement:

  • Choose a shard key with even distribution and query locality.
  • Postgres declarative range partitioning by time, dropping old partitions for retention.
  • Redis Cluster hash slots; hash tags force related keys into one slot.
  • Plan resharding.
Say thisSnagIt completions partitioned by month; {in} hash tag pins a cell to one slot (about 100k claims/s).
Know the catchHot keys. Cross-shard transactions.
20Weighted random selection and bandits

What: Pick an option with probability proportional to weights; update weights from outcomes. Bandit algorithms balance explore and exploit: epsilon-greedy, UCB, Thompson sampling.

Why it matters: The core of APMS.

How to implement:

  • Cumulative sum, one random draw, first bucket that covers it.
  • EMA update: p += lr x (success_rate - p), then normalise with a floor.
  • Better: Beta(successes+1, failures+1) sampling (Thompson).
  • Define success carefully (block signals, not every non-200).
r := rand.Float64() * total
for _, o := range opts { r -= o.w; if r <= 0 { return o } }
Say thisAPMS SelectURL and update_probabilities.
Know the catchA noisy or wrong success signal poisons learning.
Security, deploy, operate
21Authentication and authorisation: JWT, HMAC tokens, RBAC

What: JWT is a signed token with claims. HMAC tokens are server-signed values the server can verify without a lookup. RBAC grants permissions by role.

Why it matters: Zee Subdub.ai used JWT with RBAC; SnagIt uses HMAC device and work tokens.

How to implement:

  • Short expiry plus refresh tokens; verify signature, exp, audience, issuer.
  • Bind tokens to context (job id plus device id).
  • Revocation: epoch or denylist, since stateless tokens cannot be recalled.
  • Never trust client-supplied trace or role fields.
  • Compare secrets in constant time.
Say thisSnagIt epoch revocation (once never compared).
Know the catchalg=none and key confusion bugs. Long-lived tokens with no revocation.
22Real-time collaboration: Operational Transformation and CRDTs

What: OT transforms concurrent operations against each other so all replicas converge. CRDTs are data structures that merge without transformation.

Why it matters: From your Subdub.ai subtitle editor.

How to implement:

  • Server orders operations; clients transform pending ops against incoming ones.
  • Keep revision numbers; reject or transform ops on stale revisions.
  • CRDTs (Yjs, Automerge) avoid a central transform server but cost metadata.
  • Test with many concurrent editors (you tested 20).
Say thisZee Subdub.ai.
Know the catchOT transform functions are easy to get subtly wrong.
23Zero-downtime deployment and safe migrations

What: Roll out without dropping requests: rolling, blue/green, canary.

Why it matters: Resume skill.

How to implement:

  • Health checks gate traffic; connection draining on shutdown (SIGTERM, finish in-flight, then exit).
  • Deploy by immutable image digest.
  • Expand/contract migrations: add new column, dual-write, backfill, switch reads, remove old.
  • Keep old and new versions compatible during the roll (API and message schemas).
  • Switch routing by a listener rule first, flip the default last.
Say thisSnagIt ALB rules then default flip, /v2/health, arm64 pin, v1 compat shim.
Know the catchDropping a column while old code still reads it. Health check path mismatch looks like an app bug.
24Observability: logs, metrics, traces, SLOs

What: Logs say what happened, metrics say how much, traces say where time went. SLOs set a target for reliability.

Why it matters: You list Grafana, CloudWatch and distributed tracing.

How to implement:

  • Structured JSON logs with a trace/correlation id and a closed vocabulary of stages.
  • RED metrics for services (rate, errors, duration) and USE for resources.
  • Alert on symptoms (success rate, queue age), not just causes (CPU).
  • Check that an alert can actually evaluate.
  • Propagate trace ids through queues.
Say thisSnagIt 16-stage vocabulary, 3 dashboards, 18 alerts.
Know the catchHigh-cardinality labels. Alerts nobody can act on.
25Horizontal scaling and stateless services

What: Add instances instead of bigger machines; keep per-request state out of the process.

Why it matters: Resume skill.

How to implement:

  • Move state to Redis/DB/S3.
  • Scale on the right signal (requests per target, queue depth).
  • Watch downstream limits: DB connections, provider rate limits.
  • Budget connections: replicas x pool size must fit the DB.
  • Graceful shutdown for scale-in.
Say thisSnagIt 68 of 80 Postgres connections; dispatch scales to 12 replicas with no DB handle.
Know the catchScaling the front without the DB. In-memory state lost on scale-in.

27Go concurrency and runtime basics

What: Goroutines, channels, mutexes, context cancellation, sync.WaitGroup, worker pools.

Why it matters: You write Go daily.

How to implement:

  • Pass context everywhere; always cancel.
  • Bound goroutines (worker pool or errgroup with limit).
  • Close channels from the sender only.
  • Protect shared maps with a mutex or sync.Map.
  • Use graceful shutdown: stop accepting, drain, then close dependencies.
  • Avoid defer inside long loops (APMS ListenAndServe loop creates a context with defer each iteration).
