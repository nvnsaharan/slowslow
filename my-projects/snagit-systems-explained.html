Chapter 4 · SnagIt

Every system, and why it was needed

Twenty-four components of SnagIt, each with the problem it solves, what was built, what was rejected and the risk that remains.

How to read this chapter

Each system has the same four parts: the problem, what we built, the alternative we rejected, and the risk. In an interview, the "rejected alternative" is usually what earns trust.

Why the platform exists
S1Phone fleet instead of servers

Problem it solves

Grocery and ride apps block data-centre IPs and bot-like clients. Catalogue and fare data must come from places that look like real users.

What we built

Android apps run scraping jobs in the background over residential IPs on real phones. A Go core (gomobile) does the provider calls, Kotlin/Compose does the UI.

Alternative we rejected

Cloud scrapers with rotated proxies (the APMS approach). Still detectable and costly for these targets.

Know the catchThe fleet is not owned. Battery, data and consent are a deal with real people, so idle poll is 900 s and consent defaults to no.
S2Consumer comparison apps as the recruiting channel

Problem it solves

Nobody installs a scraper. People install a tool that saves money.

What we built

Comparoo (India grocery + rides), Compario (US rides), Comparion (Africa rides). Users get comparison and points; the background scraping is the exchange.

Alternative we rejected

Paying a panel of testers. Does not scale to thousands of phones.

Know the catchPlay policy and trust. FleetConsent must be explicit and revocable.
S3v2 rewrite (v1 Python/FastAPI monolith)

Problem it solves

Four of five v1 outages came from unrelated workloads sharing a process: memory, CPU, event loop, DB pool. Empty walks and late submits made phones stop.

What we built

Go, one image, four services chosen by resource profile and scaling signal. Parity tests against frozen Python oracles found four real defects during the port.

Alternative we rejected

Patch v1. The sweep that could not finish inside statement_timeout guaranteed it never would (25,667 open batches).

Know the catchRewrites are risky. The cutover on 25 Sep was rolled back and succeeded on 28 Sep.
The four backend services
S4dispatch (port 8080)

Problem it solves

Thousands of phones poll constantly. A miss is the common case (about 83% of polls).

What we built

Phone-facing API: GET /v2/work, POST result, lease heartbeat, health, plus the v1 compatibility shim and a producer API for US routes. It has no Postgres handle, by construction. Scales on requests per target, up to 12 replicas.

Alternative we rejected

Letting the API read the DB. v1 scaled on queue depth and multiplied DB connections.

Know the catchRedis or S3 down means 503 with a jittered Retry-After, never 500. The phone treats other errors as its own failure.
S5orchestrator (no port, fixed count)

Problem it solves

Something must admit batches, fill the shelf, settle results, return expired leases, and send owed messages, all bounded.

What we built

Eleven loops: intake, settler, sweep, reap, outbox, shelf, reconcile, revocations, retention, backlog, fleet. Plus US sync, scheduled notifications and app_config republisher. No leader election: SQS visibility, a Redis consumer group and SKIP LOCKED split the work.

Alternative we rejected

Advisory-lock leader election. v1's advisory-lock bug is what left 25,667 open batches.

Know the catchAdmission control is read-then-write across replicas, so it must stay a fixed count.
S6artifactworker

Problem it solves

Building a .tar.gz is CPU and memory heavy and bursty. It must not share a process with the phone API.

What we built

Reads the build queue, fetches the staged blob, builds, uploads to S3, then claims the artifact and writes the compile outbox row in one transaction. ARTIFACT_CONCURRENCY (default 4) guards memory. Scales on build-queue depth, up to 8.

Alternative we rejected

Building inside dispatch or the settler.

Know the catchA failed build is retried by not deleting the message. There is deliberately no Release method.
S7control (port 8081)

Problem it solves

Enrolment, revocation, user profile, push tokens and notifications are low-volume and security-sensitive.

What we built

POST /v2/enrol returns a device secret once. Device ids are blake2b(provider||subject). Revoke bumps an epoch. Also user endpoints and FCM sends. Admin endpoints are token-protected.

Alternative we rejected

Putting these in dispatch and widening its blast radius.

Know the catchGuestVerifier accepts any presented string (parity with v1). The v1 token bridge cannot verify tokens and is time-boxed.
Data systems
S8Redis shelf with Lua

Problem it solves

Hand each job to exactly one phone at 1,667 claims/s without a hot row.

What we built

Per job type and priority sorted sets, a jobs hash, a leases zset, lease metadata and a result stream. Six Lua scripts: claim, fill, reap, complete, extend, reclassify. Key tags like {in} keep multi-key Lua legal on a cluster.

Alternative we rejected

A Postgres queue table. Delete-on-claim at this rate is about 144M dead tuples a day. The old argument for Postgres was the eligibility predicate; evaluating it once at enqueue and encoding it into the key answered that.

Know the catchRedis is derived state. A self-managed t4g.medium has no automatic failover. The dead set also lives only in Redis.
S9Postgres ledger

Problem it solves

Need a durable source of truth for batches, requirements and completions that can rebuild the shelf.

What we built

batches, requirements, seen_messages (at-least-once guard), completions (partitioned by month), devices, outbox, app_config, scheduled_notifications. Settler writes up to 500 results in one transaction (0.018 txns per result). Retention drops old partitions.

Alternative we rejected

Writing every result synchronously (1,667 txns/s).

Know the catchShared server, no PITR. 68 of 80 connections used.
S10Outbox pattern

Problem it solves

A DB write and an SQS send cannot be one transaction. Doing both naively loses or duplicates messages.

What we built

Rows with sent_at NULL mean owed. DrainOutbox claims with FOR UPDATE SKIP LOCKED, sends, then marks sent. The draining transaction holds the locks across the send.

Alternative we rejected

Send first then write, or write then send in a separate step. Both lose or deadlock.

Know the catchAt-least-once: the receiver must tolerate duplicates.
S11SQS (intake, build, DLQ, compile, feedback)

Problem it solves

Decouple the customer from our pace and absorb bursts.

What we built

Intake carries batches of 1-50 requirements. Build queue feeds artifactworker. Compile queue notifies the customer. DLQ and redrive handle poison messages.

Alternative we rejected

Direct HTTP calls from the customer.

Know the catchIntake is shared with a legacy consumer, so the reader has no Delete method. Retention (5 h on blinkit-in) can silently delete aged work.
S12S3 (staging and artifacts)

Problem it solves

Phone result blobs can be large, and must not sit in Redis or Postgres.

What we built

Dispatch caps a blob at 8 MB, stages it to S3, and puts only a pointer on the stream. Lifecycle: staging expires after 1 day, artifacts move to IA at 7 days and Glacier IR at 30.

Alternative we rejected

Storing blobs in Redis.

Know the catchPUT cost is about $43k/month at design load with no budget alarm. Presigned uploads would fix it but need an app release.
Correctness and safety mechanisms
S13Admission control

Problem it solves

Accepting more than the fleet can finish only creates failed_due_to_sla for work never attempted.

What we built

capacity = drain_rate x deadline, with a floor of 1000. Drain rate is counted in claim.lua on the hit path (one INCR). Per-job-type admission was added later.

Alternative we rejected

Admit everything and let SLAs fail.

Know the catchNeeds a fixed orchestrator count.
S14Leases, heartbeats and the reaper

Problem it solves

Phones die mid-job. Jobs must come back without duplicating work.

What we built

Per job type leases (2700 / 300 / 900 s; 180 s for blinkit_product_listing). Heartbeat extends up to a ceiling measured from first claim. reap.lua is bounded per call, restores the original score, buries after 3 attempts.

Alternative we rejected

One global lease: too short cuts off a 30-minute walk, too long blocks a 30-second retry.

Know the catchLate genuine results return 200 as already-recorded, not 400, because three 400s ended a phone's whole run in v1.
S15Tokens and revocation

Problem it solves

Phones are untrusted, but the work endpoint must be fast.

What we built

Device token: HMAC-SHA256, 30-day max age, with an epoch. Work token: HMAC bound to (job_id, device_id), 1 h TTL, longer than the lease so a slow completion is provable. Revoke bumps the epoch.

Alternative we rejected

Server-side sessions in a DB (would put a DB on the hot path).

Know the catchThe epoch was once never compared, so revocation did nothing for up to 30 days. Fixed, and now tested.
S16Idempotency and ordering rules

Problem it solves

At-least-once everywhere means duplicates are normal.

What we built

job_id = blake2b(batch_id||msg_id). Ledger before shelf. Settle before releasing the lease. Object before message. A crash is wasteful, never silently wrong.

Alternative we rejected

Exactly-once delivery (not available).

Know the catchWasted phone work is the accepted cost.
S17Policy guards in dispatch

Problem it solves

Real fleets misbehave.

What we built

Ride quarantine (four Nigerian phones failed 317 of 340 US routes). US work window 08:00-19:50 Pacific, filled by 30-min silent pushes. Minimum version code gate. Capability resolution as a union of declared and build-known capabilities. 404 shelf_empty versus client_incompatible, each with jittered Retry-After.

Alternative we rejected

Trusting the client to be well behaved.

Know the catchMore rules means more places a job can vanish. Each needs a metric.
S18v1 compatibility shim and token bridge

Problem it solves

Installed APKs cannot be updated, and v1 tokens are not valid in v2.

What we built

v2 serves v1 paths: /routes/next, /routes/result, /auth, /app/update-config, /user/*, /rides/*. A temporary bridge covers about 5,600 devices stuck on 401, time-boxed by V1_TOKEN_BRIDGE_UNTIL.

Alternative we rejected

Force-update all clients first.

Know the catchThe bridge cannot actually verify the token.
Clients
S19Kotlin/Compose + Go core via gomobile

Problem it solves

Provider logic (TLS fingerprints, cookies, parsing) is easier and shared in Go. UI is native.

What we built

caller.aar exports one package. Hilt DI. Each provider is a Go package. Sessions stored in bbolt. Background work runs inside a WorkManager worker (a restricted foreground-service type crashed Android 15).

Alternative we rejected

Pure Kotlin or React Native.

Know the catchFive of eight provider packages have drifted between India and US copies. bbolt sessions are unencrypted.
S20On-device reliability features

Problem it solves

Phones go offline, get killed, and have limited battery and data.

What we built

ResultOutbox keeps unsent results (55 min, 50 entries, 1 MB cap). Server sets the next poll time. Network-aware caps (70 products/hour on mobile data). 404 retries after 3 s and 8 s. Silent FCM pushes start cycles. ProviderConfigSync lets the backend change hosts and headers without a release.

Alternative we rejected

Fire-and-forget upload.

Know the catchRemoving the sync toggle also removed the only battery-exemption prompt.
S21Compario engagement layer

Problem it solves

Users must get value or they uninstall and the fleet shrinks.

What we built

Room database (saved routes, price observations, savings, searches). PriceWatchWorker every 2 h, RoutineNudgeWorker hourly, WeeklyDigestWorker, three widgets that never fetch. DropRule decides when a price drop deserves a notification.

Alternative we rejected

Scraping-only app.

Know the catchNotification fatigue; DropRule must stay conservative.
Infrastructure and observability
S22ECS on Graviton, ALB, Secrets Manager

Problem it solves

Run four services cheaply and swap versions safely.

What we built

Cluster Anakin_Platform (EC2, arm64 t4g.xlarge). Image pinned to arm64 (amd64 dies with exec format error before any log). ALB snagit-backend at api.joinsnagit.com, target group snagit-dispatch-tg, health /v2/health. config.json is the single source rendered into task definitions. Deploy by image digest.

Alternative we rejected

Kubernetes or Terraform (not used in this repo).

Know the catchTask definitions are applied by hand through provision.sh because Jenkins is not wired to this repo.
S23Logging, dashboards and alerts

Problem it solves

Phones are remote, so the only way to see a job is its logs.

What we built

One JSON event format, a closed vocabulary of 16 stages, trace id carried in the Redis payload (not trusted from the device). FireLens to Loki and Grafana: three dashboards and 18 alert rules. Stage unknown flags unclassified failures.

Alternative we rejected

Distributed tracing spans.

Know the catchNo spans. Some loops were labelled stage=unknown.
S24Guard tests

Problem it solves

Config and code drift silently.

What we built

Tests recompute the Postgres connection budget from config.json, fail on config variables with unsafe defaults, check dead capabilities, check generated docs match, and fail CI if a parity suite is skipped. CI runs against real redis and postgres.

Alternative we rejected

Review only.

Know the catchArtifact parity test needs the private v1 repo, so it skips in CI.

Hot path, cold path and planes in SnagIt

Uses the words from Chapter 2.

TermIn SnagIt
Hot pathGET /v2/work and POST result in dispatch: token check, Lua claim or blob stage. No DB.
Cold pathSettler, artifactworker, outbox, retention. Phones never wait for them.
Data planedispatch plus Redis shelf carrying jobs to phones.
Control planecontrol service, app_config, revocations, admission control and the reconcile loops.
Source of truthPostgres ledger. Redis shelf is rebuilt from it.
