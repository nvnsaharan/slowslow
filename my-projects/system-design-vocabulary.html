Chapter 2 · Vocabulary

Hot path, cold path, control plane and friends

The words interviewers use to describe how a system is split up, explained in plain language. Each term has one APMS example, so you can reuse it when you talk about the project.

The one-minute version

Hot vs cold path

Hot: work a caller is waiting on. Cold: work done afterwards, where nobody waits.

Data vs control plane

Data: moves the real traffic. Control: decides the rules the traffic follows.

They cut the same system in different ways. Paths ask "is someone waiting?" Planes ask "does this carry traffic or set the rules?"

The terms

The two paths
1Hot path

The code that runs while a user or caller is waiting. Every millisecond here is felt, so it must be fast, simple and avoid slow dependencies. Think of the checkout counter in a shop.

In APMSFrom POST /api/v1/make_request until the response goes back: read weights from Redis, pick a vendor, make the proxied call, return the result. The only database work allowed is a Redis read (Mongo only on a cache miss).
2Cold path

Work that happens after the fact, off to the side, where nobody is waiting. It can be slow, batched and retried. Think of the back office that counts the till at closing time.

In APMSCounting successes and failures, batching them to SQS, and the Python updater recomputing probabilities. If it falls minutes behind, requests still work.
Mix-up to avoidCold does not mean unimportant. APMS learning lives entirely on the cold path. It just never blocks a caller.
3Warm path (and "fast path / slow path")

Some systems add a middle tier: not on the critical request, but needs results within seconds or minutes. Fast path and slow path are the same idea named differently: handle the common case quickly, push the rest aside.

In APMSThe 1-minute aggregation flush is arguably warm: it is asynchronous but time-bounded, since stale stats delay learning.
The planes
4Data plane

The part that carries the real traffic: it does the actual work the product exists for. Data plane = "what happens to each request".

In APMSThe Go selector forwarding scraper requests through proxy vendors and returning pages.
5Control plane

The part that decides the rules the data plane follows, but does not carry user traffic itself. Control plane = "how should requests be handled". It changes slowly and is allowed to be slower than the data plane.

In APMSThe per-host settings in Mongo (probabilities, on/off switch, costs, learning rate) and the Python updater that rewrites them. A human flipping a vendor switch is manual control; the updater is automated control. That is the "Automated" in APMS.
Mix-up to avoidPeople call Mongo "the database" and stop there. Name it as the control plane state and the updater as the control loop, and the design sounds deliberate.
6Management plane

Sometimes listed as a third plane: tools for humans to configure, monitor and operate the system (dashboards, admin UIs, deployment). Many teams fold it into the control plane.

In APMSClosest items are the /health endpoint and whatever you use to edit Mongo documents. APMS has no admin UI of its own.
7Why separate planes at all?

So that a failure or slowdown in the rules side cannot take down traffic. If the control plane dies, the data plane keeps running on the last known rules.

In APMSIf the Python updater stops, requests keep flowing using the last probabilities in Mongo and Redis. They just stop improving.
Mix-up to avoidThis works only if the data plane caches rules locally. APMS does that with Redis and a 5-minute TTL. But if Redis and Mongo are both unreachable, the request fails, so the independence is partial.
Loops and state
8Feedback loop (closed loop)

The system measures the result of its own decisions and uses it to change future decisions. A thermostat is the classic example. Without the measurement step it is an open loop: set once and hope.

In APMSPick vendor, observe 200 or not, adjust probability, pick again. The whole point of the project.
9Source of truth vs cache

The source of truth is the one place whose value is final. A cache is a faster copy that may be slightly stale and can be thrown away and rebuilt.

In APMSMongo is the source of truth. Redis is the cache, with a 5-minute lifetime (TTL).
10Cache-aside, TTL and cache stampede
  • Cache-aside: the app checks the cache first, and on a miss loads from the database and fills the cache.
  • TTL: time to live, how long a cached value stays before it expires.
  • Stampede: when a popular key expires and many requests all hit the database at once.
In APMSOn a miss, one request takes a Redis lock (SETNX) and reads Mongo. The others wait and poll Redis, so Mongo sees one read instead of hundreds.
11Eventual consistency

Different parts of the system may briefly disagree, but they converge if you wait. You trade instant agreement for speed and resilience.

In APMSA vendor starts failing now, and the system stops favouring it about 6.5 minutes later (1 min aggregation + 30 s batching + up to 5 min cache).
Flow and pressure
12Synchronous vs asynchronous

Synchronous: the caller waits for the answer. Asynchronous: the caller hands off work and moves on, getting results later or never.

In APMSMaking the proxied request is synchronous. Recording the outcome is asynchronous (channel, then SQS).
13Batching and aggregation

Combine many small events into one bigger message. You pay less overhead per event and lose a little freshness.

In APMSThousands of per-request outcomes become one SQS message per minute per instance, holding counts per host and vendor.
14Backpressure

What happens when a producer is faster than its consumer. Options: block the producer, drop items, or buffer more. Blocking passes the slowness upstream.

In APMSThe outcome channel holds 1000 items. If it fills, Push blocks and can slow live requests.
Mix-up to avoidOn the hot path, telemetry should never block. Dropping events with a counter is usually the right choice.
15Fail open vs fail closed

When a safety or routing component breaks, do you let traffic through anyway (fail open) or refuse it (fail closed)?

In APMSIf every vendor is switched off for a host, APMS returns an error rather than sending the request without a proxy. That is fail closed, and it protects your own IP address from being exposed or banned.
16Exploration vs exploitation

Use what looks best now (exploit), or try alternatives to learn whether they are better (explore). Too much exploitation locks you onto a stale favourite. Too much exploration wastes traffic.

In APMSWeighted random choice means weaker vendors still get a share of requests, which keeps learning alive.
17Stateless vs stateful

Stateless: an instance keeps nothing that matters between requests, so you can add or remove copies freely. Stateful: it holds data you would lose or have to move.

In APMSSelector instances are nearly stateless, with one exception: the in-memory one-minute stats window, which is lost if an instance dies.
18Latency vs throughput

Latency is how long one request takes. Throughput is how many requests per second the system handles. Optimizing one can hurt the other.

In APMSBatching raises throughput of the cold path at the cost of freshness. The hot path is tuned for latency: cache first, no database writes.

Say it in an interview

"The request path is the hot path and stays minimal: a Redis read, a weighted pick and the proxied call. Outcomes go to a cold path through a channel and SQS, where a Python job updates probabilities. That job is the control plane, so the data plane never waits on learning, and if the control plane stops, traffic keeps running on the last known rules."

The Mongo, Redis and SQS details come from the APMS source code. Terms are standard industry vocabulary and different companies draw the lines slightly differently, so ask what an interviewer means if a term is used loosely.
