APMS: Automated Proxy Management System

Eighteen questions an interviewer could ask about this project, with answers grounded in the code. Green boxes are what to say out loud. Amber boxes are weak spots you should name before they do.

The 30-second pitch

APMS is a proxy gateway for our scrapers. A caller sends one JSON request to POST /api/v1/make_request. The service picks a proxy vendor for the target host, makes the request through it, and returns the response.

It also learns. Every outcome is counted per host and per vendor, and a background job nudges each vendor's selection probability toward its recent success rate. Vendors that work for a site get more traffic. Vendors that get blocked get less, with no human tuning.

Questions and answers

Grouped by what an interviewer is probing.

Problem and design
Q1What problem does it solve?

We scrape many sites through several paid proxy vendors (the code has geonode, brightData, smartProxy and proxyverse). Which vendor works best depends on the target site, and vendors have different prices. Hard-coding one choice either burns money or gets blocked. APMS picks a vendor per request and adapts as results come in.

Say thisIt turns proxy selection from a static config into a feedback loop, per target host.
Q2Walk me through one request end to end.
  • The handler parses the JSON (method, URL, headers, payload, timeout, country code). Timeout above 30 s is rejected.
  • The service takes the URL's host and loads that host's proxy settings: Redis first, Mongo on a miss.
  • It picks a vendor by weighted random choice among vendors switched on, optionally rewrites the proxy URL for the requested country, and builds a fresh TLS client with a random browser fingerprint.
  • It sends the request. If the status is 200 it records a success, otherwise a failure, by pushing a small event onto an in-process channel.
  • The response is decoded (gzip, brotli, deflate) and returned. Non-200 responses come back as a JSON error with that status.

proxy_service.go · client_utils.go · response_utils.go

Q3Why split into a Go service and a Python service?

They have different jobs. The request path is latency sensitive and high concurrency, and the TLS-fingerprinting client library (bogdanfinn/tls-client) is a Go library. The learning step is not latency sensitive, runs on a timer, and reuses our internal Python SQS helpers. SQS between them means the learner can be slow, restart, or fall behind without affecting live traffic.

Say thisHot path stays in Go and never waits on the learner. They only share data through SQS and Mongo.
Q4Why is the state keyed per host?

A vendor that is excellent on one site can be blocked on another. Each Mongo document is keyed by host and holds the vendor probabilities, vendor URLs, an on/off switch per vendor, and a learning rate. A host with no document falls back to a default document. On the first update for a new host, the updater inserts a copy of the default, so each new site starts from the default weights and then diverges.

stats_repository.py · getDocument / putProbabilites

The learning algorithm
Q5How does the system learn? Give me the formula.

For each vendor that received traffic in the window, with success rate s = success / (success + failure):

p += lr_eff × (s − p)

That is an exponential moving average pulling the vendor's probability p toward its observed success rate. Afterwards all probabilities are normalized to sum to 1, with a floor of 1e-6 so nothing hits exactly zero. Vendors with no traffic in the window are skipped.

Say thisIt is a lightweight reinforcement scheme: reward-driven probability matching, not a full bandit algorithm like UCB or Thompson sampling.

stats_aggregator.py · update_probabilities, normalize

Q6What is the cost factor and why is it squared?

lr_eff = learning_rate × min_cost / cost². The cheapest vendor gets the full learning rate. A vendor that costs 2x as much learns at a quarter of the speed. Costs live in a separate Mongo document and are cached for 5 minutes.

The intent is to be conservative about shifting traffic toward expensive vendors.

Know the catchThe factor slows learning in both directions. An expensive vendor that starts failing also loses probability slowly. A cleaner design puts cost into the reward (success per dollar) and keeps the learning rate constant.
Q7How does it balance exploration and exploitation?

Selection is random in proportion to the probabilities, so a vendor with 10% weight still gets about 10% of requests and keeps producing fresh evidence. The 1e-6 floor stops any vendor being permanently dead. A manual switch field per vendor (on/off) lets an operator remove a vendor outright.

Know the catchProbability matching keeps sending a fixed share of traffic to weak vendors, and recovery of a vendor sitting near the floor is slow. Epsilon-greedy with decay, UCB, or Thompson sampling would explore more efficiently.
Q8How is a vendor actually picked on each request?
  • Keep only vendors whose switch is "on".
  • Build a cumulative sum of their probabilities and divide by the total, so it works even if the on-vendors do not sum to 1.
  • Draw one uniform random number and take the first bucket that covers it.

If every vendor is off, it returns an explicit "no proxy available" error for that host instead of sending the request unproxied.

client_utils.go · SelectURL

Q9What counts as a success? Is that a good signal?

HTTP 200 is success. Any other status is a failure, including 404, redirects and 429.

Know the catch
  • A 404 on a valid proxy is not the proxy's fault, but it lowers that vendor's score.
  • If client.Do errors out (connection refused, proxy auth failure, timeout), the function returns before pushing any stat. Hard network failures are never counted against a vendor.
  • A 200 that contains a captcha page still counts as success.
Say thisNext step is classifying outcomes: block signals (403, 429, captcha body) and transport errors count against the vendor, ordinary 404s are ignored.
Concurrency and reliability
Q10How do you avoid hammering Mongo when the cache expires?

This is the cache stampede problem. On a Redis miss, a request tries SETNX lock:<host> with a 10 s expiry. The winner re-checks the cache (double-checked locking), reads Mongo, writes Redis with a 5 minute TTL, and releases the lock. Everyone else polls Redis every 100 ms for up to 5 s. So many concurrent requests for the same host cause one Mongo read.

Know the catchThe lock value is a constant "1" and release is a plain delete. If the holder is slower than 10 s, it can delete a lock now owned by someone else. A unique token plus a compare-and-delete script fixes that.

proxy_service.go · getProxyDocument · cache.go

Q11Why aggregate in memory and batch to SQS instead of sending one message per request?

Per-request messages would mean one SQS call per scrape. Instead each request pushes a tiny event to a buffered channel (capacity 1000). A single goroutine drains it into a host → proxy → {success, failure} map under a mutex. Every minute a ticker serializes the whole map as one SQS message and resets it. The updater then batches again for 30 s before touching Mongo.

The cost is delay and a small loss window: on a crash you lose up to about a minute of counts. For a statistical signal that is acceptable.

queue.go · aggregator_service.go · consumer.py

Q12What happens if that channel fills up?

Push blocks until there is room or the request's context is cancelled. So a stalled aggregator would apply back-pressure and slow live requests.

Know the catchFor telemetry, dropping events is the safer choice. A non-blocking send with a default case (and a dropped-events counter) keeps the hot path independent of the feedback path.
Q13How long until a bad vendor stops getting traffic?

Worst case adds up across the stages:

StageDelay
Selector aggregation windowup to 1 min
Updater batch windowup to 30 s
Redis TTL on settingsup to 5 min
Totalroughly 6.5 min

For an emergency, the on/off switch in Mongo removes a vendor immediately for new cache loads, or after the 5 minute TTL for cached hosts.

Q14How does it shut down and what state is at risk?

It listens for SIGINT and SIGTERM, stops accepting requests with a 5 s server.Shutdown, stops the aggregator goroutines, then closes Mongo and Redis. Mongo and Redis handles are singletons made with sync.Once, and the Mongo handler pings and reconnects (3 tries, 2 s apart) before each operation.

Know the catchStopping the aggregator does not flush the current partial window to SQS, so up to a minute of stats is dropped on every deploy.
Scraping specifics
Q15Why create a new client with a random TLS profile for every request?

Anti-bot systems fingerprint the TLS handshake (JA3 and similar), and Go's default TLS stack is easy to flag. tls-client imitates real browser handshakes. Each request picks a random profile and gets a fresh cookie jar, so requests do not share an identity.

Know the catchNo connection reuse, so every request pays a full TLS handshake. A random profile can also disagree with the User-Agent header the caller sends, which some sites check.
Q16How does country targeting work?

Residential proxy vendors encode geography in the proxy username. The stored URL has no country, and addCountry rewrites it per vendor: for geonode and brightData it inserts -country-XX before the second colon of the URL, for proxyverse it inserts country-XX after http://, and for smartProxy it leaves the URL unchanged.

Know the catchThis is string slicing on credentials. A vendor with a different format, or a malformed URL, can panic or produce a bad URL. Per-vendor URL templates in config would be safer.
Scale and next steps
Q17What breaks when you run many instances?
  • Selector instances are stateless apart from the in-memory window, so they scale horizontally. Each sends its own aggregate message.
  • The Python updater reads a document, computes new probabilities, and writes them back. Two consumers processing the same host in the same moment would overwrite each other's update (lost update).
  • Fixes: run one consumer, or apply updates atomically ($inc on raw counters in Mongo and compute probabilities from counters), or partition the queue by host.
Q18What would you improve first?
  • Better outcome signal: count transport errors and block signals, ignore benign 404s.
  • Use retries: a MaxRetries = 3 constant exists but nothing reads it. On failure, retry once or twice through a different vendor instead of returning the error.
  • Cost-aware reward (success per dollar) instead of scaling the learning rate.
  • Proper bandit: Beta-Bernoulli with Thompson sampling needs only the success and failure counts already collected.
  • Non-blocking telemetry and a final flush on shutdown.
  • Safe lock with ownership token, and metrics on per-vendor success rate and latency.
Say thisI would start with the outcome signal, because every learning improvement depends on it being correct.
