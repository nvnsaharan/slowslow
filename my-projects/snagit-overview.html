Chapter 3 · SnagIt

SnagIt: what it is and what we achieved

A phone-fleet data collection platform: three Android apps, a four-service Go backend, Redis and Postgres. This chapter gives the pitch, the picture, the numbers and the honest gaps.

The 30-second pitch

SnagIt is a data-collection platform for a B2B customer who needs grocery catalogue and ride-fare data that blocks data-centre scrapers. Instead of scraping from servers, the work runs on a fleet of real consumer Android phones on residential IPs. The phones belong to users of our price-comparison apps (Comparoo in India, Compario in the US, Comparion in Africa), who get a free comparison tool.

The backend sits between two parties that never talk to each other. The customer's producer publishes batches of requirements to SQS. Thousands of phones poll an HTTP API for one job at a time, do it, and post the result back. We turn results into a .tar.gz in S3 and tell the customer's compiler.

The two-minute version

Problem. v1 was a Python/FastAPI monolith. Four of its five outages came from unrelated workloads sharing one process. Phones were also being rejected on empty walks and late submits.

What we built. v2 is Go, one image run as four services split by resource profile: dispatch (phone API), orchestrator (background loops), artifactworker (builds files), control (enrolment and notifications). Redis holds a "shelf" of ready jobs with the invariants in Lua. Postgres is the ledger and source of truth. SQS and S3 carry intake and output.

Why it holds up. One atomic ZPOPMIN guarantees a job goes to one phone. Deterministic job ids make every retry idempotent. Ledger is written before the shelf, and settled before a lease is released, so a crash costs wasted work and never silent loss.

Result. Measured on a laptop: 47,345 req/s at p99 3.4 ms from one dispatch process. v2 has been serving the whole fleet since 28 Sep 2026.

How this project can be asked

Interviewers rarely say "explain SnagIt". They pick an angle. Prepare one 60-second answer for each.

AngleTypical questionYour anchor answer
ScaleHow would it handle 10,000 polls per second?Dispatch has no DB handle. A miss costs a few O(1) ZPOPMIN calls. 62,828 claims/s measured on a laptop.
CorrectnessHow do you make sure a job runs on exactly one phone?Lua claim script, atomic ZPOPMIN, then deterministic job ids, status-transition claim at settlement, outbox.
FailureWhat if Redis dies? What if a phone vanishes?Shelf is derived state, rebuilt from Postgres. Leases expire and the reaper requeues, buries after 3 attempts.
TradeoffWhy Redis and not Postgres for the queue?Delete-on-claim at 1,667/s makes about 144M dead tuples a day. Eligibility is encoded in the key at enqueue.
OwnershipWhat did you personally build?See "My part" below. Pick two things and go deep.
HindsightWhat would you change?Presigned uploads, Redis failover and backups, fleet-wide rate limiter, real load test, Android CI.
Product / ethicsIs it OK to run scraping on users phones?Consent defaults to no, collection starts only after yes, Play policy driven.

What is left to achieve

Reliability

Redis failover and backups (self-managed t4g.medium today). Dedicated Postgres with point-in-time recovery. Persist the dead set outside Redis.

Scale and cost

A real end-to-end load test. Presigned uploads to cut about $43k/month of S3 PUTs at design load. Fleet-wide per-provider rate limiter.

Security

Retire the v1 token bridge. Real enrolment verification instead of guest. Redis TLS. Narrow the task role from SQSFullAccess. Encrypt provider sessions on device.

Engineering hygiene

Android CI. One shared Go module for provider packages (5 of 8 have drifted between India and US). Refresh stale docs and READMEs.

Honest gaps to name before they do

Say these yourself
  • Work that ages past SQS retention is deleted silently. The blinkit-in queue keeps messages 5 hours, not the 14 days the design assumed. Detection exists, the fix needs another team.
  • The fleet drains about 9.3 jobs/s while supply can be 1,667/s, so admission control caps what we accept.
  • A cell is pinned to one Redis slot (about 100k claims/s ceiling).
  • Some docs lag reality. CUTOVER-READINESS.md still describes the 25 Sep rollback, while the later deployment doc and commits say v2 has served the fleet since 28 Sep.
  • The Africa app has no backend cell yet, so its scrape loop is inert.
